## 一、致命：陀螺被自己的卡尔曼滤波高通掉了

**文件**：`Drivers/imu.cpp`

**改了什么**
删掉三个无条件跟踪 `rawGyro` 的 `KalmanFilter<float>(0, 1e-6f, 0.01f)`，
以及 `correctedGyro = rawGyro - gyroBias - filtered` 这条减法。
换成两级去偏：

1. `gyroBias` —— 静态零偏，`setupIMU()` 上电自动标定一次（新接进流程，此前 `calibrateGyroOnce()` **没有任何调用者**，`gyroBias` 恒为 0），CLI `cg` 可重标；
2. `gyroBiasTrim` —— 温漂微调，**三重门控**才更新：未解锁 + 角速度模长 < 0.05 rad/s(≈2.9°/s) + 连续满足 1000 帧(1s)；低通系数 0.0005（τ≈2s），硬限幅 ±0.035 rad/s。

**为什么是致命 bug**
`K_ss = 0.00995`（τ≈100ms），"信号减去它自己的低通"就是一个截止频率约 **1.6Hz 的高通**。
数值仿真（滤波器收敛后再以恒定 100°/s 旋转）：

| 时间 | 真实转角 | 旧代码积出的转角 | 角速率反馈 |
|---|---|---|---|
| 0.05 s | 5° | 3.9° | 60.7°/s |
| 0.10 s | 10° | 6.3° | 36.8°/s |
| 0.30 s | 30° | 9.5° | 5.0°/s |
| 1.00 s | **100°** | **9.95°** | ≈0 |
| 5.00 s | 500° | 9.95°（不再增长） | 0 |

渐近上限 = ω/(K·f) = 100/(0.00995×1000) = **10.05°**。
即：任何持续转动都被当成"零偏"吃掉，内环角速率反馈等效开环，姿态环无论怎么调 PID 都救不回来。

**为什么之前没被发现**：VOFA+ 画的是 `mpu9250_read_data()` 的**原始**输出，高通发生在画图之后。
现在 `imuPlot()` 改画去偏、去安装旋转之后控制环真正使用的 `gyro`/`acc`（13 通道顺序不变）。

**怎么验证**
`plot on` → 拆桨 → 手持机体绕 X 轴匀速转 2 秒。
通道 4（gyro X, deg/s）应该**整段保持在实际转速附近**，通道 7（roll, rad）应该单调增长到对应角度。
旧固件的表现是通道 4 在 0.3s 内塌到 0、通道 7 卡在 ~0.17rad(10°) 不动。

## 二、致命：失控保护的自动下降原本是"永久悬停"

**文件**：`application/control.cpp`、`application/safety.cpp`

**改了什么**
`interpretControls()` 的三档模式映射加了 `if (mode != AUTO)` 守卫；
`autoFailsafe()` 的杆量变化判定从"精确相等"改为四轴统一 0.02 死区（油门沿用 0.05）。

**为什么是致命 bug**
控制链顺序是 `interpretControls() → interpretWebRC() → failsafe()`，`failsafe()` 里的 `descend()` 才把 `mode` 设成 `AUTO`。
旧版 `interpretControls()` 无条件用模式通道改写 `mode`，于是下一周期 `mode` 立刻被改回 `STAB`，
`descend()` 的 `if (mode != AUTO)` 每帧都成立 → 6 个 PID 被反复 reset、`thrustTarget` 被反复钳回 0.7、
减掉的 `dt/descendTime` 又被钳回去。

结果：**遥控丢失 / 低电量触发的自动下降永远降不下来，飞机以 70% 推力一直悬停到电池耗尽。**

只有网页遥控场景侥幸没暴露——`setWebRCInput()` 把 `controlMode` 写成 `NAN`，三档比较对 NAN 全为假，`mode` 才保得住 `AUTO`。
**物理遥控一旦接通（见第五条），这个 bug 立刻变成实弹**，所以两条必须一起改。

`autoFailsafe()` 是同一问题的另一半：SBUS 11bit 通道即使摇杆不动也会抖 ±1~2 LSB，
精确相等比较等于"人工接管"被噪声每帧触发，`descend()` 照样走不完。

退出 AUTO 的唯一途径现在是 `autoFailsafe()`（杆量明显变化）或网页遥控的模式/急停按钮。

**怎么验证**（拆桨）
1. 网页遥控解锁、给一点油门，然后关掉浏览器页面；
2. 观察 8s 后应打印 `Web RC连接丢失，启动下降`，`plot on` 看通道 11（thrustTarget）在 10s 内**线性**从 0.7 降到 0；
3. 到 0 时应自动上锁（通道 13 = 0）。
旧固件的表现是通道 11 卡在 0.7 不动。

## 三、MPU9250 采样率与滤波配置全错

**文件**：`Drivers/mpu9250.cpp`、`Drivers/mpu9250.h`

| 寄存器 | 改前 | 改后 | 效果 |
|---|---|---|---|
| `SMPLRT_DIV` | 7 → **125Hz** | 0 → **1kHz** | 与控制环同频，不再一帧读 8 次重复值 |
| `CONFIG`(陀螺 DLPF) | 0x06 → **5Hz / 33.48ms 延迟** | 0x03 → **41Hz / 5.9ms** | 33ms = 滞后 33 个控制周期，P=6 的外环必然振荡 |
| `ACCEL_CONFIG_2` | **从未写入** → 默认 460Hz / 6ms | 0x03 → **41Hz / 11.9ms** | 电机振动不再几乎不滤波就进积分 |
| `PWR_MGMT_1` | 最后写 | **最先写**（+10ms 等 PLL 锁定） | 按数据手册推荐顺序，先唤醒再配置 |
| `PWR_MGMT_2` | 未写 | 显式写 0x00 | 确保三轴加计+陀螺都使能 |

代码注释里"DLPF_CFG=0x06 对应约 21Hz 带宽"是编的——数据手册表里没有 21Hz 这一档。
两张完整的 DLPF 表（陀螺 7 档 / 加计 7 档，含带宽与延迟）已抄成 `mpu9250.h` 里的 `MPU9250_DLPF_*` / `MPU9250_ADLPF_*` 宏，答辩讲"为什么选 41Hz"可以直接引用。

顺手删掉了空壳 `mpu9250_set_rotation()`（只打日志、从不生效），安装旋转统一由 `imu.cpp` 依据 `IMU_ROT_*` 施加。

**怎么验证**：启动日志应出现
`reg readback: DIV=0x00 CONFIG=0x03 GYRO=0x10 ACCEL=0x18 ACCEL2=0x03 PWR=0x01`。
这行也是判断 SPI 写链路是否真的通的最好依据（全 0x00 = 写不进去）。

## 四、网页控制台 JSON 拼装的栈溢出

**文件**：`Bsp/web_rc.cpp` `handler_console_get()`

**改了什么**：改用两个带钳位的 lambda（`jsonPut` / `jsonPutStr`）拼装，`cap = sizeof(json)-1`，`pos` 永不越界。

**旧代码为什么危险**
```c
pos += snprintf(json + pos, sizeof(json) - pos, ...);
```
`snprintf` 返回的是**未截断时本应写入的长度**。一旦截断，`pos` 就会超过 `sizeof(json)`；
随后 `sizeof(json) - pos` 以 `size_t` 计算发生**回绕**，变成一个巨大的长度参数，
下一次 `snprintf` 直接写穿栈 → httpd 任务栈溢出 → 复位或更糟。
循环末尾的 `json[pos++] = '"'` 和 `json[pos] = '\0'` 更是完全没有边界检查。

触发条件：控制台缓冲攒满（50 行 × 240 字节）后一次 `limit=50` 的拉取。不算罕见。

**怎么验证**：网页控制台跑一堆长输出命令（例如反复 `p`），然后 `limit=50` 拉满，观察不重启、JSON 仍然合法。

## 五、SBUS 遥控链路整条重写

**文件**：`Drivers/rc.cpp`（全文重写）、`Bsp/board_config.h`、`application/parameters.cpp`

改前是"接了接收机也完全没反应"的哑故障，五个独立缺陷叠在一起：

| # | 改前 | 改后 |
|---|---|---|
| 1 | `rcProtocol = 1`（CRSF），而 CRSF 分支只是"攒够 10 字节就丢掉"的空壳 | 默认 0=SBUS；`setupRC()` 检测到非 0 会**强制回退并打印告警**，不再静默失效 |
| 2 | UART 配成 8N1 / `rcBaud`(420000) | 按协议固定 **100000 / 8E2**，并 `uart_set_line_inverse(UART_SIGNAL_RXD_INV)` 内部反相（可参数关闭） |
| 3 | 11bit 解包写错：`temp = byte & 0x7FF`（对 uint8_t 是空操作）、`temp \|= (byte & 0x7F) << 11`（应为 `<<8` 且取低 3 位），且 `idx` 每 2 字节才 +1 去对 22 字节数据区 | `sbusUnpack()` 按位正确解 16×11bit |
| 4 | 帧同步只看起始字节，不校验结束字节和 flags | 25 字节定长收帧 + 结束字节校验 + `failsafe`/`frame_lost` 标志位拒收 + 前 4 通道量程合理性检查 |
| 5 | `normalizeRC()` 只写 `rollChannel` 等中间量，**从不进 `controlRoll`** | 两段式归一化后直接写 `controlRoll/Pitch/Yaw/Throttle/Mode` 并刷新 `controlTime` |

其它连带修正：

- **模式通道值域错了**：旧版映射到 `[0,2]`，而 `interpretControls()` 用 `<0.25 / <=0.75 / >0.75` 三档判断，值域必须是 `[0,1]`。后果是三档开关的中位(≈0.83)和高位(≈2.0)都落进 `>0.75`，**`flightModes[1]` 永远选不到**。现在映射到 `[0,1]`。
- **`channelZero` 语义修正**：它是通道**中位**不是零点（旧默认 999/2099 是占位值）。参数名 `RC_ZERO_*` → `RC_MID_*`，默认值改成 SBUS 标准的 992/1811；改名也顺带让 NVS 里残留的占位值自动失效。最小值按对称行程推导 `2*mid - max`，并在 `channelRange()` 里做合法性校验（参数被写坏就回退默认值，否则 `mapf` 分母可能为 0 或负数）。
- **`calibrateRC()` 从空函数变成真标定**：10 秒实测各通道 min/mid/max，行程不足 200 的通道跳过（说明没动过），已解锁时拒绝执行，标定期间 `rcCalibrating=true` 让 `normalizeRC()` 只更新 `channels[]` 不写控制量。
- **删掉 `RC_ROLL/RC_PITCH/RC_THROTTLE/RC_YAW/RC_MODE` 五个参数注册**。它们是每帧都被覆盖的实时遥测值，不是可调参数；物理遥控一旦接通，`syncParameters()` 的"值 != 缓存就写 NVS"会以 1Hz 持续擦写 flash（NVS 页擦写寿命有限，等于慢性损坏）。
- 新增参数 `RC_INVERTED`；`rcUartPort` 改用 `BOARD_RC_UART_NUM`（此前硬编码 `UART_NUM_1`，板级宏形同虚设）。
- 删掉空壳 `calibrateRCChannel()`。

**控制权归属规则（新）**：只要有合法物理遥控帧，**物理遥控就是主控**，网页遥控让位。两路同时在线时打印一次提示。想用网页飞就别开发射机。

**怎么验证**：`rc` 命令看 `good=` / `bad=` 帧计数与 `RC signal`。
两个都是 0 → 查接线/对码/共地；`bad` 涨而 `good=0` → 十有八九是反相反了，试 `p RC_INVERTED 0` + `reboot`。
拿到信号后先 `cr` 标定，再 `plot on` 看通道跟随。
