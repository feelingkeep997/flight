## 0. 先建立正确认知（10 分钟，别跳过）

**这个项目是什么**
- 多任务飞控固件，约 7000 行 C++，五层目录：`User/`(入口) `application/`(飞行逻辑) `Middlewares/`(公共库) `Bsp/`(板级/通信) `Drivers/`(外设)。
- 构建：ESP-IDF **v5.1.6**，`sdkconfig:220` → `CONFIG_IDF_TARGET="esp32"`（经典 ESP32，走 `Bsp/board_config.h` 的默认引脚分支）。
- **任务结构**（`application/freertos_demo.cpp`，本节旧版写成"单体 super-loop"已不适用）：`app_main()` → `setup()` 顺序初始化 → `freertos_demo()` 派生 `startTask`，后者建三个工作任务后自删。
  - `controlTask` 优先级 10、绑核 1、`vTaskDelayUntil` 固定 **1kHz**：`readIMU → step → estimate → control → sendMotors`；
  - `commTask` 优先级 5、核 0、1kHz 轮询：`readRC / readWebRC / 控制台命令队列 / handleInput / processMavlink`；
  - `housekeepingTask` 优先级 2、核 0、200Hz：电池电压 / 日志 / `syncParameters`(NVS) / LED。
  - 跨任务同步只有三个原语：`targetMutex`（保护 attitudeTarget/ratesTarget/thrustTarget/armed 这一组）、`controlPaused`（`pause()` 挂起控制环，电机测试用）、`attitudeResetRequested`（CLI `reset` 的请求标志，由控制任务自己执行复位）。其余 `float`/`int` 单字量靠 ESP32 上对齐 32bit 访问天然原子，不加锁。

**三个必须提前知道的"事实修正"**（否则会把力气花错地方）
1. `README.md:7-43` 的目录结构是**旧的**（写的是 `main/` + `components/...`），实际以 `CMakeLists.txt` 为准；`README.md:54-57` 还把 ACRO 标成"自稳"、STAB 标成"定高"，与代码不符（代码：ACRO=纯角速率，STAB=姿态自稳，ALTHOLD=定高，见 `application/control.cpp:83`）。
2. **串口遥控器（SBUS）链路已于 2026-10-09 修通**（此前是断的：`normalizeRC()` 只写 `rollChannel` 等中间量，从不进 `controlRoll`；SBUS 按 8N1/420000 配置且 11 位解包写错；`calibrateRC()` 是空函数；`rcProtocol` 默认还是未实现的 CRSF）。现在：`setupRC()` 按 SBUS 物理层配 100000/8E2/RX 反相，`sbusUnpack()` 按位正确解 16×11bit，`normalizeRC()` 两段式归一化后直接写 `controlRoll/Pitch/Yaw/Throttle/Mode` 并刷新 `controlTime`。**控制权规则：只要有合法物理遥控帧，物理遥控就是主控**（网页遥控让位），想用网页飞就别开发射机。写 `controlRoll` 的地方现在有三处：`Drivers/rc.cpp`、`Bsp/web_rc.cpp`、`Middlewares/mavlink.cpp`（MANUAL_CONTROL）。
3. `Bsp/espnow.cpp` 有 212 行完整实现，但**不在 `Bsp/CMakeLists.txt` 的 SRCS 里**，且 `ESPNOW_ENABLED` 宏无处定义 → 当前不参与编译。这正是"ESP-NOW-only 方案"的落点。

**读码方法（本工程专属捷径）**
每个 `.cpp` 头部都有固定五段中文注释：`职责 / 关键逻辑 / 输入输出 / 重要参数 / 边界情况与潜在风险`。
→ **永远先读文件头注释，再进函数**；它已经是作者留给你的地图。学完一个模块后，再回头读头注释，检验自己是否真的看懂了。

### 1.3 VOFA+ 曲线（已有链路，直接用）
FireWater / 115200，由 `Drivers/imu.cpp` 的 `imuPlot()` 输出。**COM 号不固定**（CH340 随插拔和 USB 口变化，见过 COM4/COM5/COM6），连之前先用设备管理器或 `python -m serial.tools.list_ports` 确认，选错口就是什么都收不到。
**默认关闭**：上电不发数值行，串口只有初始化信息与 CLI 菜单；要看波形先敲 `plot on`（`plot` 查状态，`plot off` 关，`quiet` 一次关掉 plot+trace）。
这里改过三轮：最初 `IMU_DEBUG_PLOT` 硬编码常开 **100Hz**，13 通道 ≈ 93 字节/行 ≈ 9.3 kB/s，占 115200 波特率(11.5 kB/s)的 **81%**，会把 failsafe / 定高 / HTTP 的 `print()` 挤在 512 字节 TX 环里排队甚至丢掉，所以 2026-10-09 改成默认关闭；后来又试过"默认开启但降频"（地面 50Hz≈40%、解锁后 10Hz≈8%），但 17 通道数值行仍然会刷屏、打断串口助手里人可读的日志，因此最终定为**默认关闭、需要时手动打开**。
另一个变化：画的**不再是芯片原始值**，而是去偏、去安装旋转之后控制环真正使用的 `gyro`/`acc`。旧版画 raw，所以当去偏环节把角速度滤成高通时，VOFA+ 上一切正常、姿态却纹丝不动，等于没调。
**注意：是 13 个通道，不是 9 个**（`imu.cpp` 里 `imuPlot()` 的注释即权威顺序）：

| # | 通道 | 单位 |
|---|---|---|
| 1-3 | acc x/y/z | m/s² |
| 4-6 | gyro x/y/z | **deg/s**（代码内部是 rad/s，输出前乘了 180/π） |
| 7-9 | 姿态 roll/pitch/yaw | **rad** |
| 10 | velZ | m/s |
| 11 | thrustTarget | 0~1 |
| 12 | hoverThrustEst | 0~1，未激活发 `-1` |
| 13 | armed | 0/1 |

采样上限 50Hz（`IMU_DEBUG_PLOT_HZ`），解锁后自动降到 10Hz（`IMU_PLOT_ARMED_HZ`），且它直写 UART0 绕过 `print()`，所以会和 CLI 文本混在一起 —— 不看了就 `plot off`（或 `quiet` 一次关掉 plot+trace）。两级开关：运行期用 CLI `plot on/off`（默认 off，改完即生效，不用重编译）；想彻底不参与编译才去改 `Drivers/imu.cpp` 里的 `IMU_DEBUG_PLOT` 为 `0`。

## 3. 阶段 2：感知——从 SPI 字节到姿态（2 天）

**读**（按数据流顺序）：
`Drivers/mpu9250.h` → `Drivers/mpu9250.cpp`(240) → `Drivers/imu.cpp`(257) → `Middlewares/vector.h`(173) → `Middlewares/quaternion.h`(261) → `Middlewares/lpf.h`(67) → `application/estimate.cpp`(125)

**先记住这些硬件锚点**（读代码时用来对照）
- WHO_AM_I 接受 **0x71/0x73（MPU9250/9255）或 0x70（MPU6500）**（`mpu9250.cpp:216`、`imu.cpp:124`）。**不支持 MPU6050（0x68，且 MPU6050 没有 SPI）** —— 平时口头叫"MPU6050"，写文档/答辩时要说 MPU9250 系。
- SPI：SCK=18 / MISO=19 / MOSI=23 / CS=5，**10MHz**，HSPI 主机（`board_config.h:127-130`、`mpu9250.cpp:51-78`）。
- 量程：gyro **±1000 dps**、acc **±16g**（`imu.cpp` 的 `configureIMU()`）。灵敏度在 `mpu9250.cpp` 的 `mpu9250_read_data()` 里硬编码：陀螺 **32.8 LSB/(°/s)**、加计 **2048 LSB/g**（旧版笔记写成"2048 LSB/(°/s)"是错的）——**改量程必须同时改这两个常数**，否则角度/加速度会成比例错。
- **采样与滤波（2026-10-09 已改，别再照抄旧值）**：`SMPLRT_DIV=0` → 输出率 **1kHz**（与控制环同频）；陀螺 `CONFIG=MPU9250_DLPF_41HZ(0x03)` → 带宽 41Hz / 延迟 **5.9ms**；加计 `ACCEL_CONFIG_2=MPU9250_ADLPF_41HZ(0x03)` → 采样 41Hz(3dB 27Hz) / 延迟 11.9ms。
  改之前是 `SMPLRT_DIV=7`(125Hz) + `CONFIG=0x06`（陀螺 **5Hz / 33.48ms** 延迟，注释里写的"约21Hz"在数据手册里根本不存在），而且 `ACCEL_CONFIG_2` **从未被写过**，加计跑在寄存器默认的 460Hz/6ms。33ms 的陀螺延迟 = 姿态环滞后 33 个控制周期，P=6 的外环必然振荡发散——这是本机一直没能离地的两个主因之一。
  两张 DLPF 表都抄在 `Drivers/mpu9250.h` 的宏注释里，答辩讲"为什么选 41Hz"可以直接引用。
- 一次 burst 读 14 字节从 0x3B 起（`mpu9250.cpp:134-160`），gyro 在 buffer[8..13]（这里历史上踩过 off-by-one）。

**链路复述（能背下来就算过关）**
raw → `readIMU()`：减 `gyroBias`（上电 `calibrateGyroOnce()` 标定的静态零偏）→ 减 `gyroBiasTrim`（只在"未解锁 + 连续 1s 角速度 < 2.9°/s"时才更新的温漂微调，硬限幅 ±2°/s）→ acc 减 `accBias` 乘 `accScale` → 按 `imuRotation` 旋转 → 写入全局 `gyro`/`acc`

> **⚠️ 2026-10-09 修掉的头号 bug，答辩可以当"问题定位过程"讲**：
> 旧代码在这里放了三个 `KalmanFilter<float>(0, 1e-6f, 0.01f)` **无条件**跟踪 `rawGyro`，然后 `correctedGyro = rawGyro - gyroBias - filtered`。稳态增益 K≈0.00995（τ≈100 样本 = 0.1s），"信号减去它自己的低通"恰好就是一个截止频率约 **1.6Hz 的高通**：
> 恒定 100°/s 持续转动时，角速率反馈按 `(1-K)^n` 指数衰减（τ≈100ms），姿态角最多只能积到 **ω/(K·f) ≈ 10.05°** 就停住不动。数值仿真（滤波器已收敛后开始转）：0.05s 积出 3.9°(真值 5°) → 0.1s 积出 6.3°(真值 10°) → 0.3s 积出 9.5°(真值 30°) → **1s 积出 9.95°(真值 100°)**，之后永远不再增长。任何持续角速度都被当成"零偏"吃掉 → 内环角速率反馈等效开环 → 姿态环无论怎么调 PID 都救不回来。
> 它和上一条的 5Hz/33.5ms 陀螺 DLPF 叠在一起，就是"重构后从未成功离地"的完整解释。
> **教训**：零偏只能在确认静止时估计；调试波形必须画控制器真正看到的量，画 raw 会把这个 bug 完美藏起来。
→ `estimate()` 内部固定顺序：`applyGyro()`（去零偏+低通+四元数增量旋转）→ `applyAcc()`（**仅 `landed` 时**用重力方向以 `accWeight=0.003` 慢修）→ `applyLevel()`（默认 `levelWeight=0` 即关闭）→ `estimateVelZ()`（机体系→世界系、去重力、积分 + 泄漏 `ALT_VEL_LEAK=0.15`）。

## 4. 阶段 3：控制——三个环与混控（3 天，毕设核心）

**必答题**

   （**2026-10-09 补充**：`controlTorque` 的怠速分支现在多了一个 `idleLatch` 闩锁——解锁后**必须先推过油**（`thrustTarget >= motThrMin`）才允许进入"收油到底保持 10% 怠速"；没推过油时电机保持 0。旧版是"一解锁四路立刻钉在 10%"，而解锁手势本身要求油门最低，等于拿着飞机一解锁桨就转，同时 `descend()` 的最后一段也被这个分支顶住停不下桨。上锁即复位闩锁。想清楚：为什么这道闩锁不会让"空中收油"变得不安全？）
4. `desaturate()` 为什么保均值、压差量？代价是什么（大机动时总推力被压低 → 掉高度）？（`control.cpp:299-312`）
5. 电机下标语义：`MOTOR_*` 索引 **0=RL, 1=RR, 2=FR, 3=FL**，而 `BOARD_MOTOR_PINS {12,13,15,14}` 不是顺序排列（`motors.cpp:61-64` + `board_config.h:119`）→ 实际 RL=GPIO12、RR=13、FR=15、FL=14。手推一遍并把结论写进笔记；`cli.cpp:191` 的 `mot` 打印顺序也和下标不同，别被误导。⚠️ **这四个电机引脚里有两个是 ESP32 的 strapping（启动配置）引脚，不是"要确认一下"而是必须先搞清楚**：
   - **GPIO12 = MTDI，最危险**。上电瞬间为高电平，ROM 会把 SPI flash 供电电压设成 1.8V，而模块上的 flash 是 3.3V → **直接启动失败**（串口无输出或一片乱码）。MOSFET 直驱时栅极一般有下拉电阻，静态为低是安全的；但换成带内部上拉的驱动、或栅极下拉缺失/开路，就会踩雷。
   - **GPIO15 = MTDO**。上电为高会打开 SDIO slave 时序并让 ROM 在 UART0 输出启动日志；为低则抑制启动日志。不会导致启动失败，但"看不到 boot log"往往就是它被电机电路拉低了。
   - **GPIO2（板载 LED）也是 strapping 引脚**，上电必须为低或悬空才能进下载模式。若 LED 接法是 GPIO2 → 限流电阻 → 3.3V（灌电流），上电会被拉高，得按住 BOOT 再按 RST 才能烧录。
   这些是硬件事实，软件绕不过去；`Bsp/board_config.h` 默认分支上方已写了同样的警告。**改引脚号之前先对着 `SCH_E1 Mini V1.3Y_K_2026-09-19.pdf` 核实驱动电路。**
6. PWM 细节：LEDC_TIMER_0 + 低速模式 + `LEDC_AUTO_CLK`，通道 0..3 == 电机下标，**25kHz / 10bit**，`pwmMax=-1` ⇒ 走"纯占空比"分支 `duty=round(v*1023)`（`motors.cpp:54-58,80-127`）。想接标准 ESC 的 µs 模式，就把 `MOT_PWM_MAX` 设成 ≥0。
7. ALTHOLD：无气压计怎么"定高"？为什么松杆能收敛到悬停油门（`altHoldI=0.3` 在线学 `hoverThrustEst`）？为什么 >30s 后不可信？（`control.cpp:211-239` + `estimate.cpp:69-80`）

**动手**

**保护链（顺序即优先级，`safety.cpp:54-62`）**
`rcLossFailsafe`(1s) → `webRCLossFailsafe`(8s) → `autoFailsafe` → `invertedFailsafe`(cos<−0.7 持续 1.5s) → `batteryFailsafe`。
`descend()` 是**全工程唯一**把 `mode` 设成 `AUTO` 的地方：先复位 6 个 PID，把 `thrustTarget` 钳到 `ALTHOLD_HOVER_THRUST=0.7`，再按 `dt/descendTime(10s)` 线性减到 0 后 `armed=false`（`safety.cpp:79-100`）。

> **⚠️ 2026-10-09 修掉的第二个致命 bug（失控保护原本是"永久悬停"）**
> 控制链顺序是 `interpretControls() → interpretWebRC() → failsafe()`。旧版 `interpretControls()` **无条件**用模式通道三档映射改写 `mode`，而 `failsafe()` 在它之后才把 `mode` 设成 `AUTO`。于是下一周期 `mode` 立刻被模式通道改回 `STAB`，`descend()` 的 `if (mode != AUTO)` 每帧都成立 → 6 个 PID 被反复 reset、`thrustTarget` 被反复重新钳回 0.7、减掉的 `dt/descendTime` 又被钳回去。
> 结果：**遥控丢失/低电量触发的自动下降永远降不下来，飞机以 70% 推力一直悬停直到电池耗尽**。只有网页遥控场景侥幸没暴露——因为 `setWebRCInput()` 把 `controlMode` 写成 `NAN`，三档比较对 NAN 全为假，`mode` 才保得住 `AUTO`。物理遥控一旦接通（见上一条），这个 bug 立刻变成实弹。
> 修法：`interpretControls()` 里 `if (mode != AUTO)` 才做三档映射。退出 AUTO 的唯一途径是 `autoFailsafe()`（杆量明显变化 = 人工接管）或网页遥控按钮。
> 连带修的还有 `autoFailsafe()` 的死区：旧版对 roll/pitch/yaw 用**精确相等**比较，而 SBUS 11bit 通道即使摇杆不动也会抖 ±1~2 LSB，等于"人工接管"会被噪声每帧触发，`descend()` 照样走不完。现在四轴统一 0.02 死区（油门沿用 0.05）。
> **答辩可讲的点**：这是典型的"多输入源 + 状态机被上游无条件覆盖"缺陷，只在特定输入组合下暴露（网页遥控 NAN 掩盖了它），靠单条链路测试永远测不出来。
电量阈值：`VBAT_WARN 3.5 / LOW 3.3 / CRIT 3.0 / ABSENT 0.5`（`globals.h:197-202`）；飞行中(<0.15 推力除外)跌破 3.0V 触发下降，地面跌破 3.5V 直接禁止解锁。

**参数系统**：注册表 `parameters[]`（`parameters.cpp:60-176`，含 `CTL_*`、`ALT_*`、`EST_*`、`IMU_*`、`MOT_*`、`SF_*`、`WIFI_*`/`MAV_*`），NVS 命名空间 **"flix"**，`syncParameters()` 只在 **1Hz 且不活跃时**写、只写变化项（`parameters.cpp:247-259`）。`preset` 会 `nvs_erase_all` + 重启，**连带抹掉 WiFi 凭证**。

**MAVLink 现状（毕设答辩可能被问到）**：手写 **v1** 帧（`0xFE`，无官方库）。发 HEARTBEAT(0)/EXTENDED_SYS_STATE(245) @2Hz，ATTITUDE_QUATERNION(31)/RC_CHANNELS_RAW(35)/ACTUATOR_CONTROL_TARGET(26)/SCALED_IMU(26)/SERIAL_CONTROL(126) @10Hz。
